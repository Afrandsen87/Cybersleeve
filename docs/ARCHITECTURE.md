## Deploy changelog
`.github/workflows/deploy.yml` runs `scripts/collate-changelog.mjs ${{ github.event.before }}` before the checks, then `biome format` on the result. The script reads `changelog.ts` as it was at the previous push to `main` (`git show`) and the commit subjects since (`git log --no-merges <sha>..HEAD`), and calls the pure `deployChangelog` (`src/build/collateChangelog.ts`):
- If entries were added by hand since then (a `version` label not in the old file), `collateChangelog` replaces them by ONE entry: the newest new label, the changes of all new entries oldest first, exact duplicate lines dropped. The commit subjects are then ignored (hand-written text is curated; mixing both would list a change twice).
- Otherwise `commitLines` turns the commit subjects into changelog lines (oldest first, duplicates dropped; subjects starting `chore:`, `docs:`, `test:`, `refactor:`, `ci:`, `build:`, `wip:`, `internal:` and merge commits are skipped) and they become ONE new entry on top, labelled with the deploy time (UTC, `YYYY-MM-DD HH:MM`, supplied by the script).
- `renderChangelogSource` writes the array back. The commit-subject convention is a standing rule in `CLAUDE.md`. This is build-time only: the deployed game shows one entry, nothing is committed and the repository keeps the individual entries. With fewer than two new entries, no baseline (manual run, first push, force push) or an unknown sha, the file is left alone and the step succeeds. If a deploy is cancelled by a newer push, the next run's baseline is that cancelled push, so its entries stay separate. The rewrite is deterministic text merging; an LLM rewrite could be added behind the same function shape but is not built. Needs Node 22.18+ (runs the `.ts` files directly).

## Layering (dependencies point downwards only)
```
main.ts ── ui/dom.ts ── ui/viewModel.ts
              │              │
       ui/widgets/*    ui/view/*   (one file per widget / per view)
   │            │              │
   ▼            ▼              ▼
app/ (createGame, loop, persistence)  ──►  core/  ──►  numbers/ (BigNum interface)
                                     content/ (data)        │
                                                            ▼
                                              BreakInfinityNum (only file importing break_infinity.js)
```
- `numbers/` – `BigNum`/`NumberFactory` interfaces, the break_infinity.js adapter, `formatBigNum`.
- `core/` – pure game rules, no DOM, no timers, no storage. Time enters only via `GameEngine.tick(deltaMs)`. The heat skills are split by responsibility: `heatEffects.ts` (their registry entries, spread into `EFFECTS`), `heatPace.ts` (the pure cooling pace: idle factor, Mole aggregation) and `heat.ts` (tax and cooldown maths, including the tax cap). `GameEngine` is a thin facade over small units, none of which it builds itself (they are injected; `app/createGame.ts` is the one place that wires them): `DerivedStats` (all read-only calculations), `ActionRunner` (access gating, start costs, run progress, closed-form completion), `NetworkSystem` (passive income, growth), `cooldowns.ts` (heat and Legend decay), `Progression`, `Shop`, `Economy` (formulas) and `OverflowPolicy`. The outside world depends only on narrow interfaces in `api.ts`: `GameQueries` (read-only; used by the view model; the union of `StateQueries`, `ActionQueries`, `SleeveQueries` and `ShopQueries`, so a consumer or a test fake can depend on just the part it reads) and `GameCommands` (what a player can do: `startAction`, `activateBuyable`, `augmentAction`, `giveUpForMoles`, `sellItems`, `resleeve`, `newGame`). Scalar state (credits, network, heat, ...) is described once as data in `fields.ts`; that table drives the initial state, re-sleeving, saving/loading and overflow repair. `rewards.ts` holds one descriptor per reward kind (the scalar it pays, whole units per run, whether `global.creditMultiplier` scales it, whether it may be paid per node); `effectRegistry.ts` is the registry of buyable effects: ONE entry per effect kind holding its traits (needs an action, can be switched on and off), its validator and the hooks that add it to an action or to the sleeve; `effects.ts` loops over the owned buyables and calls those hooks, so it has no `switch` over kinds, and `effectTraits.ts` is a view of the registry plus `assertNever`. `infinity.ts` defines the game's infinity, 1e308, which the overflow policy and every saturating multiplier use. `backChannel.ts` (`BackChannel`) turns items into Moles, `Shop.toggle` switches auto-runs, so the engine mutates no state itself. Skill trees: `ui/view/skillTree.ts` (`buildSkillLanes`, pure) puts the skills (and the re-sleeve skills) in lanes by `branch`, places each on a grid (column = depth through `parents`; rows come from the tree of first parents: each childless skill takes the next free row, so every path is its own lane, and a parent is centred on its children, possibly on a half row) and decides which are readable (own `requires` owned and every parent readable; the rest are masked as `???`); `ui/widgets/skillTree.ts` (`mountSkillTree`) draws a tree once, sideways, with CSS variables `--col`/`--row` and SVG edges in grid units, and a refresh only toggles classes and text. Content: one file per branch in `content/buyables/skillBranches/`. Skills: `skills.ts` (`earnedSkillPoints`: 0 while all levels are 0, then 1 + floor(log10(total of action levels))); the `Shop` pays `skillPoints` purchases from `earned - cost of the skills owned` (nothing is stored), and `Progression` applies `actionXpReduction` to action levels the way it applies `sleeveXpReduction` to sleeve levels. Heat cooling with a skill speed and Moles is `coolHeatBoosted` (`heat.ts`, closed form; `moles` is a scalar of the state). Augments: `Augments` (`augments.ts`) applies one schematic from the inventory to an action (`GameEngine.augmentAction`), counted per rarity in `ActionState.augments` (`Record<rarityId, number>`); `DerivedStats.xpPerRun` multiplies the action XP by `augmentXpFactor` (additive within a rarity, `1 + n x bonus`, and the rarities multiply each other), and `ActionRunner` pays that, so batches stay closed-form. Items: `Inventory` (add drops, take and sell stacks) and `ItemDrops` (rolls what a batch of runs drops; the drop rules come from `DerivedStats.itemDrops`, i.e. from owned `itemDrop` buyables) with `sampling.ts` (`binomial`, `multinomial`, `RandomSource`). Overclock and Focus: four effect kinds, two per action (`overclockUnlock`, `focusUnlock`: action hooks that set `ActionEffects.overclockUnlocked` / `focusUnlocked`) and two sleeve-wide (`overclockStrength`: `SleeveStats.overclockStrength = 1 + perCopy x copies`; `focusSlots`: `SleeveStats.extraFocusSlots`, added to `focus.baseSlots`; what Focus gives is the `focus` section of the configuration) and two flag maps in the state (`overclocked`, `focused`, per action id, off at first, reset by re-sleeving, saved and sanitised on load against what is owned). `DerivedStats.overclockStatus` / `focusStatus` say what each is for an action (they return `null` until the action has bought the unlock, so there is no switch to show); they feed two extra `SpeedModifier`s (`overclock`, `focus`, factor `1 + bonus`, 1 while off) through `SpeedContext`, so the speed stays one product. An action's `OverclockRule` is a mix of gains (`speedBonus`, `rewardBonus`: scaled by the strength) and fixed costs and extras (`heatPerMinute`, `heatPerRunFactor`, `completionEffects`, `alsoPays`), so each action can have its own; `OverclockStatus` carries the resolved values, `DerivedStats.activeOverclock` is the status while the switch is on, `DerivedStats.rewardMultiplier` includes `1 + rewardBonus`, and `ActionRunner.completeRuns` applies the heat factor, the completion effects and `payAlso` (the other action's reward for the same number of runs) in closed form. `ActionToggles` (`actionToggles.ts`) switches them (`GameEngine.toggleOverclock` / `toggleFocus`; Focus needs a free slot). The heat Overclock costs is charged by `ActionRunner.tick` for the time `advance` reports the action ran, so it is closed form and tick size does not matter. `ZeroDays` (`zeroDays.ts`, configured by `items.zeroDay`, toggle in `GameState.zeroDaysOn`) holds the Zero-day toggle (`GameEngine.toggleZeroDays`) and settles a batch of completed runs in `ActionRunner.completeRuns`: `claim` takes `min(runs, held)` Zero-days from the inventory and those runs are critical for sure, the rest roll the normal chance (`CriticalSuccesses`); the toggle switches itself off at 0 held, and is saved (read back as off when none is held). `CriticalLinks` (`criticalLinks.ts`) keeps the bank of guaranteed critical successes (`GameState.bankedCriticals`): a `criticalLink` buyable (Ransomware) makes each critical run of its action `bank` one for a target action, and the target's next completed runs `claim` them (`min(runs, banked)`, closed form) before Zero-days and the critical chance are considered. `criticalBoost` (Persistence) multiplies the critical rule in `DerivedStats.criticalRule`; `overclockHeatFactor` (Obfuscation) lowers `OverclockStatus.heatPerRunFactor` through `SleeveStats.overclockHeatFactors`. `BurnLeads` (`burnLeads.ts`) uses one Burn lead from the inventory (`GameEngine.useBurnLead`; configured by `items.burnLead`): it takes `heatFraction` of the current heat away. Heat is a plain number that may hold fractions; `coolHeat` / `coolHeatBoosted` (`heat.ts`) remove it in whole points only (a small epsilon absorbs floating-point dust) and the cycle bar waits while there is less than one point. `diagnostics.ts` is the channel for "time had to be dropped" warnings. State is exposed only as a read-only `GameStateView` (`DeepReadonly<GameState>`, derived, never hand-copied).
- `content/` – `gameConfig.ts`: the single tuning file (actions, buyables, progression, speed, global levers, engine, runtime). See `docs/CONFIG.md`. Add content and retune here.
- `app/` – composition root (`createGame`), timer loop with injected `Scheduler`, `SpeedToggle` (x10 test fast-forward), `SaveGame` with injected `KeyValueStore` (`createBrowserStore` falls back to memory when `localStorage` is blocked), `createNewGameHandler` (the temporary "Reset save" button).
- `ui/` – **Inventory (2026-10-26):** the tip of every row lists where its stack drops from (`DerivedStats.dropSources`, exposed as `GameQueries.dropSources`: per action that can drop it, the chance of one completed run, computed from `itemDrops` so chance multipliers and rarity shifts are included). `InventoryView.rows` has a row for every item and rarity (`InventoryRowView`: label, `symbol` fallback, `rarityIndex`, count, `sellable`, `usable`, `canUse`, `backChannel`, tip); `dom.ts` draws them as tiles (`buildInventoryWidget` / `renderInventory`): kept or used items in one section, sellable ones in a section to the right whose tiles are selected by clicking (`InventoryWidget.selected`, a choice of the screen only) and acted on by the Sell, Sell all and Back channel buttons beside the grid; clicking a usable tile (Burn lead) calls `GameCommands.useBurnLead`. **Icons (2026-10-25):** the pixel art is data in `content/icons.ts` (16x16 grids of characters, a palette, and `ENTITY_ICONS`, which says which icon an action, item or the credits shows). `ui/pixelIcon.ts` (pure, tested) turns the grids into SVG data URLs once at start-up (`createIconSource`); `dom.ts` takes the lookup as `MountOptions.icons` (default: none) and gives the element a `has-icon` class and a `--icon` custom property, which `style.css` paints in a `::before` box, so replacing an element's text never removes its icon. New icon: add a grid and a line in `ENTITY_ICONS`; the content test fails when an action, item or the credits has none. `uiText` (every word the interface shows, as one table that is injected; names are placeholders), `viewModel` (pure, tested; stat widgets are lists of `StatRowView` and the Sleeve section layout is computed once per config) and `dom` (thin binding that builds stat widgets from those rows; covered by happy-dom tests). The test aids bar (a bar at the top of the page, in the layout flow so it never covers the tabs) is shown only in development builds or with `?debug` in the address (`app/debugControls.ts`). `dom` only places what the view model says and sends commands; it holds no game rules (whether a click buys or switches an auto-run is `GameCommands.activateBuyable`). Every frame writes only what changed. **Render cost (2026-10-25):** the screen is drawn by `app/renderLoop.ts` on the display's frame clock (`requestAnimationFrame`, rate-limited by `runtime.renderMs`, skipped while the page is hidden); the game itself still steps on a timer. **The square (2026-10-26):** each action card has a square beside its reward line and its two level bars, under the full-width run bar (`ActionView.square`, an `ActionSquareView` of four `SquareCellView`s: Auto-run, Overclock, Focus, Augment). While Auto-run is not owned the whole square is one button that buys it; afterwards it is a 2x2 grid in which a cell is a purchase (`mode: 'buy'`, the unlock buyable), a toggle (`'toggle'`), the Augment press (`'press'`) or an empty placeholder (`'empty'`). The view model flags the buyables that live in the square (`BuyableView.inSquare`: effect kinds `autoRun`, `overclockUnlock`, `focusUnlock`) so `dom.ts` leaves them out of the row of purchases; `dom.ts` builds both the big button and the grid once (`buildSquare`) and `renderSquare` shows one of them and updates the cells from the view. Hover texts are built only when shown: the view model exposes them as getters (`tip`, `speedTip`, `backChannelTip`; `StatRowView.hasTip` says whether a row has one), `dom.ts` registers them in a `TipRegistry` (`ui/tooltip.ts`) that writes the `data-tip` marker attribute once, and the tooltip box asks the registry on hover and re-reads the visible one after each refresh (no `MutationObserver`). Bars are full-width fills scaled with `transform: scaleX()` and a CSS transition of `--render-ms`; a bar that goes down snaps back instead of sliding. `buildViewModel` runs inside `engine.snapshot(...)` (`core/snapshot.ts`), in which the sleeve stats and skill points are computed once; `LevelRule` keeps its exact thresholds and its last level lookup. **Tabs (2026-10-25):** two centered tabs at the top, Character and Skills (`TabView`; the active tab is kept in the DOM layer only, not in the game state and not saved). Character holds the layout below; Skills holds a box with the skill buttons and the points available. The credits header sits above both panels. Desktop layout (changed 2026-10-25): a top band with the **Sleeve widget** (global stats + global buyables) on the left and, to its right, the Network widget beside **Sleeve Improvements** (the sleeve-wide purchases paid in credits: Rebuyable / One-time) and **Network Exploitation** (those paid in nodes), all three of equal width and equal height, with the Inventory widget under them (the band stretches so its widgets fill it without gaps); the purchases were moved out of the Sleeve widget; a line across the screen separates the band from the 3x2 grid of action cells below it (unused cells are empty placeholders).

## SOLID in practice
- **S** – `Progression` (XP/levels, including reduced sleeve XP requirements), `Shop` (purchases in credits or nodes), `effects` (buyable effects), `speed` (multiplier), `serialization`, `GameLoop`, `SaveGame` each have one job; `GameEngine` only orchestrates (see Layering).
- **O** – new speed factors = new `SpeedModifier`; new content = data in `gameConfig.ts`; a new scalar stat = one entry in `fields.ts` (plus the `GameState` field); a new reward kind = one entry in `REWARDS` (the compiler demands it); a new effect kind = a union member and ONE entry in the effect registry (`effectRegistry.ts`; the mapped type demands it, so a forgotten kind does not compile). A kind with a dedicated query (network growth, level bonus, XP reductions, drop chance, back channel) leaves the hooks out and is read by that query. There is no global reward multiplier: a lever applies to one named kind of reward (today only `global.creditMultiplier`, for credits).
- **L** – anything satisfying `BigNum`, `Scheduler`, `KeyValueStore`, `ResleevePolicy`, `Tickable` is substitutable (tests use fakes).
- **I** – small interfaces (`Scheduler`, `Tickable`, `KeyValueStore`, `ResleevePolicy`).
- **D** – the engine receives its collaborators through the constructor; game code never imports break_infinity.js.

## Domain model
`GameState` = the scalars of `fields.ts` (credits, network (nodes), `iceRating`, `nodePayoutBonus` (credits per second added to the base value of a node by Push malware) and `hackingProficiency` as `BigNum`s because multipliers can make them unbounded; heat, `heatCooldownMs`, `legend`, `legendCooldownMs` and `networkRemainder` as plain numbers because their effects saturate or are bounded), `autoRunOff` (auto-run switches), `overclocked` and `focused` (the per-action Overclock and Focus switches), per-action `{xp, sleeveXp, runsTowardSleeveXp, augments, running, progress}`, copies owned per buyable (`purchased: Record<id, number>`), and the `inventory` (`Record<itemId, Record<rarityId, number>>`, whole counts as plain numbers capped at the largest exact integer). Items (`ItemDefinition`) and rarity tiers with their sell values (`RarityDefinition`) are content in `GameConfig.items`. Definitions (`ActionDefinition`, `BuyableDefinition`) are separate from state. Sleeve XP/level is per action. A buyable either belongs to one action (`BuyableDefinition.actionId`, displayed inside that action's card) or, with no `actionId`, to the sleeve (displayed in the Sleeve widget). Sleeve-wide effects (`interfaceSpeed`, `accessLevel`) are resolved by `resolveSleeveStats` into `SleeveStats` (access level, interface speed, heat), exposed as `GameEngine.sleeveStats()`; Interface speed is a `SpeedModifier` (a plain multiplier on every action's speed); heat is a tax on earned credits (`heatTaxFactor` with `sleeve.heatTaxPerPoint`, applied through `Economy` to run payouts and passive income) that cools down by `heatCooldownAmount` every `heatCooldownMs`, in whole points only and only while there is at least one whole point (`coolDownHeat` in `cooldowns.ts`, closed form so long ticks are cheap); access level gates actions (`ActionDefinition.requiredAccessLevel`, `GameEngine.isUnlocked`). An action's `rewardKind` decides whether a run pays credits or network nodes; nodes produce passive credits (`network.creditsPerNodePerSecond`).

## Tick loop
`setTimeout` (50 ms; keeps firing in background tabs) → `GameLoop.step` (real elapsed time × `timeScale`, capped at 10 min) → `GameEngine.tick(delta)` → the tick is cut into slices of at most `engine.maxSliceMs` (at most `engine.maxSlicesPerTick` slices); for each slice: passive network income (`nodes × rate × slice × heat-tax factor`, nodes owned at the start of the slice) → network growth → heat cooldown and Legend decay (closed form) → for each action (skipped while locked by access level): apply auto-run, advance progress, then complete runs **in batches** (below) → `OverflowPolicy.apply` → `render()` (skipped while `document.hidden`). A step that throws is reported (`onError`, default `console.error`) and the loop carries on.
**Progress of a run.** `ActionState.progress` is the share (0 up to, not including, 1) of the current run that is done. Each step takes `(1 - progress) x duration` to finish at the speed of the moment, so a change of speed only changes the rest of the run. A tolerance of `1e-9` of a run (`PROGRESS_EPSILON` in `actionRunner.ts`) stops floating-point rounding from keeping a finished run waiting. The save format is version 6; only the current version is read.

**Batches (closed form).** All runs between two level changes are identical in speed and reward, so they are applied at once: `n = min(runs that fit in the time left, Progression.runsBeforeLevelChange)`. A batch pays its reward in full (`n × reward`; heat taxes only the credits network nodes produce, so a run's payout does not fall as heat rises), adds `n × heat`, and records `n × XP` and `n` counted runs. A tick therefore costs about one batch per level gained, not one iteration per run; `maxBatchesPerTick` is only a safety net. A manual run that completes drops leftover time; an auto-run carries it into the next batch.

**Automation.** `Automation` (`core/automation.ts`) owns the unlocks and settings in `GameState.automation` (saved, reset by re-sleeving) and runs once per slice after the actions (`GameEngine.advance`): Auto Burn computes the number of leads that brings heat to the ceiling (`BurnLeads.useMany`), autosale sells whole stacks of the switched-on rarities (`Inventory.sell`), dispersal splits the schematics held by largest remainder (`Augments.applyMany`). Points are not stored: `pointsEarned` sums the owned `automationPoints` buyables (`automationPointsEarned`) and `pointsAvailable` asks the `Shop` (earned minus the price of the owned buyables paid in the `automationPoints` currency, the automation skills). **Unlocked is derived, not saved:** a feature is unlocked when the buyable with the effect `unlocksAutomation` for it (the first skill of its lane, `isFeatureUnlocked`) is owned, and `unlock(feature)` (the screen has no unlock button; the player clicks the skill) buys that skill through the injected `AutomationShop`. The lanes are skills with `branch` = the feature id, drawn inside each feature's box by `ui/widgets/automationWidget.ts` with the same `buildSkillLanes` / `mountSkillTree` as the Skills tab (`panelViews.automationView`). The screen reaches the unit through `GameQueries.automation()` (an `AutomationControls`). Save version 5 dropped `automation.unlocked`; version 6 deliberately wiped all earlier saves (no migration is kept).

**Critical successes.** `CriticalSuccesses.settle(runs, covered)` settles a batch with two binomial draws (runs that carry +100% from a Zero-day, Admin key or banked success, and those that do not): the whole part of the chance is that many sure successes per run, the fraction a chance of one more, a covered run has one more for sure. It returns the total number of successes and the runs that got none; the runner pays `plainRuns x reward + successes x rewardMultiplier x reward` and teaches `plainRuns + successes x xpMultiplier`. `CritFeed` (`core/critFeed.ts`, advanced by the engine with every slice, never saved) remembers the last second of successes per action for the card highlight.

**Cybernetics skill effects (units).** `CriticalSuccesses.settle` ends with one more binomial draw: each success brings one extra, free success with `SleeveStats.criticalExtraChance` (`criticalExtraChance` buyables; the extras do not roll again, so `DerivedStats.maxCritsPerRun` doubles while one is owned). `DerivedStats.criticalRule` multiplies the rule's `rewardMultiplier` (not its XP) by `SleeveStats.criticalRewardFactor` (`criticalRewardMultiplier`). `LinkedPayouts` (`core/linkedPayouts.ts`, injected into `ActionRunner`) draws once per batch how many whole rewards of another action a source action's runs also pay (`paysActionReward`, rules in `SleeveStats.paysActions`, read by `DerivedStats.paysActions`); `ActionRunner.completeRuns` pays them with `payAlso`, so they never crit and carry no XP, heat or drops. `DerivedStats.rewardMultiplier` also multiplies by `levelRewardFactor` (`core/levelRewardFactor.ts`: `1 + coefficient x ln(1 + level / scale)` per owned `rewardMultiplierFromActionLevel`). `interfaceSpeedFromAugmentRarities` is a sleeve hook that multiplies `interfaceSkillFactor` by `1 + perRarity x distinctAugmentRarities` (`augments.ts`, passed to `resolveSleeveStats` as `augmentRaritiesHeld`).

**Item drops.** Chance cannot be rolled run by run when a batch holds millions of runs, so `ItemDrops.roll(action, n)` draws the number of drops directly from Binomial(n, chance) and splits them over the rarities with a multinomial draw (`sampling.ts`: exact up to 1000 runs, Poisson or normal approximation above). A batch of any size costs the same. The randomness is an injected `RandomSource` (`Math.random` in `createGame`, a seeded one in tests). Rules are read when the runs complete, so a rule that changes over time applies to later runs. `DerivedStats.itemDrops` hands out the rules with their weights as they stand now: a `rarityShiftFromProficiency` buyable shifts them with `shiftWeights` (`rarityShift.ts`), one step per whole order of magnitude of Hacking Proficiency. One long tick and many short ones give the same drop rate, not the same drops (it is random); `items.test.ts` checks the rate.

**Tick granularity and slicing.** Within a slice passive income and heat cooling use the nodes and heat at the start of the slice, and heat added by runs starts cooling in the next slice. Systems that feed back on themselves (interface speed rising with every run, heat cooling while the network pays) would drift if a long tick were computed in one go, so a tick longer than `engine.maxSliceMs` is cut into slices that run one after another. Result: one long tick and many short ones agree (`batching.test.ts` checks interface speed within 2% over 5 minutes and passive income under cooling within 1% over 50 minutes, and that without slicing the first would be clearly off). The cost of a tick is bounded by `engine.maxSlicesPerTick`; beyond that the slices simply get longer and the agreement degrades gracefully. Runs of actions with a start cost still complete one per batch (a share-of-balance cost has no exact closed form because of rounding), so `maxBatchesPerTick` caps them per slice.

## Number handling (replaces the reference game's workarounds)
All amounts are `BigNum` (mantissa/exponent). The adapter treats exponent ≥ 9e15 (library saturation) as non-finite, so overflow is detectable. **Infinity is 1e308** (`core/infinity.ts`, decided 2026-10-26): it sits just under the largest double, so the plain-number multipliers (interface speed, node payout, the speed product) and the `BigNum` amounts overflow at the same place instead of the doubles plateauing silently long before the amounts do. No iteration over huge counts (runs are batched, see Tick loop), no rounding hacks. After every slice the `OverflowPolicy` repairs non-finite scalars and XP; the default clamps every amount above 1e308, and positive overflow, to 1e308 (the largest safe integer for plain-number scalars) and calls an optional `onInfinity` listener when an amount sits at infinity and turns negative overflow and **NaN into 0** (NaN is a bug upstream and must never become a windfall) so the state stays valid and saveable. The real reaction, the "infinity" prestige, is not designed yet: the listener is its hook. Level calculation uses `floorLog10`, exact at powers of ten and valid beyond the double range (tested up to 1e1000).

## The Corporation
`Corporation` (`core/corporation.ts`) starts and advances the corporation's actions (`GameConfig.corporation`, `corporationTypes.ts`); its progress is `GameState.corporation` (`corporationState.ts` creates, writes and reads it; it is on the carry-over list of `state.ts`, so a re-sleeve keeps it). It is a separate unit from `ActionRunner` on purpose: a corporation run takes exactly `baseDurationMs` (no `DerivedStats`, no interface speed, Focus or Overclock) and `GameEngine.advance` ticks it right after the character's actions. A completed run applies its effects through the registry in `corporationEffects.ts` (`CORPORATION_EFFECTS`, typed over every kind, so a new kind needs one entry; `validateConfig` asks the same handlers to check their configuration). `upgradeRandomItem` draws the successes with `binomial` and the stacks they come from with one `multinomial` over the stacks that have a next rarity (the injected `RandomSource`), then moves items with `Inventory.take/add`. `Corporation.durationMs` divides `baseDurationMs` by `levelFactor(speed.actionLevel, level)`; owned `addsCorporationEffect` buyables of an action (`BuyableDefinition.corporationActionId`) apply their effect after the action's own on each completed run (`acquireStock` raises `CorporationState.stocks`, saved and read as 0 when missing). The card shows them (`CorporationActionView.buyables`); the Holdings widget is a stat widget (`CorporationView.holdings`). Corporation actions have action levels (`CorporationLevels` in `core/corporationLevels.ts`: the XP is `CorporationActionState.xp`, saved as a string and read as 0 when missing; the rule is a `LevelRule` over `progression.actionLevels`; `Corporation.tick` awards `xpPerRun` per completed run; no sleeve levels; a level does not change the run time yet; shown as a level bar on the card). The corporate rank (`Corporation.rank`: `corporation.baseRank` plus the owned `corporateRank` purchases) gates the actions (`requiredRank`); the effect has the `corporate` trait, which keeps its buyable out of the Sleeve widgets and in the Asset Acquisition widget (`isCorporate` in `buyableViews.ts`), and is on `CARRIED_OVER_BUYABLE_EFFECTS`. The corporation is open while a buyable with the `unlocksCorporation` effect is owned (`Corporation.isUnlocked`). In the UI, `ui/view/corporationView.ts` builds `ViewModel.corporation` (the widget rows are placeholder constants until the corporation has state: rank 1, no owned corporations, no employees; the widgets beside it are titled Holdings, Asset Acquisition and Hostile Negotiation and are empty) and `ui/widgets/corporationPanel.ts` draws the tab; the tab itself comes from `tabsView`.

## Re-sleeving and synthetic sleeves
**Re-sleeve skills** (16, four lanes in `content/buyables/resleeveBranches/`: retention, reach, synthetics, corporation; ids in `content/resleeveSkillIds.ts`). Their effect kinds are in `core/resleeveEffectTypes.ts` (the `ResleeveEffect` part of `BuyableEffect`) with one registry entry each in `core/resleeveEffects.ts` (spread into `EFFECTS`, like `heatEffects.ts`). `BuyableCaps` (`buyableCaps.ts`) resolves how many copies of a buyable may be owned: its `maxPurchases` plus the `buyableCapBonus` skills (Clearance Escalation: Access upgrade; Deep Conditioning: Faster conditioning, whose floor of runs falls one run per extra copy in `Progression.runsPerSleeveXp`); the `Shop`, save loading and the invariants all ask it. `focusStacking` (Overdrive Cap) sets `SleeveStats.focusStacking`; `GameState.focusStacks` holds the slots beyond the first per action, `DerivedStats.focusStatus` counts the slots (`count`, `canAdd`, `canRemove`; the speed bonus is `(1 + bonus)^count - 1`) and `ActionToggles.addFocus` / `removeFocus` change them; the Focus cell then carries a `split` view and the card draws two half buttons over it. Synthetics: `SynthSleeves` reads `synthsPerResleeve` (Cloning Vats, `addForResleeve`) and `perfectCopies` (each sleeve earns at least the network's own income, passed in as a function so it needs no `DerivedStats`); `interfaceSpeedPerLnSynths` (Hive Interface) is a sleeve hook; `synthXpBoost` (Neural Mirror) sets `SleeveStats.synthXpFactor` and `DerivedStats.xpPerRun` applies it while the action's level is below `bestSynthActionLevel` (runs are cut at level thresholds, so the factor is constant inside a batch); `Resleever` writes `SleeveRunRecord.actionLevels`. Corporation: `Corporation.workersFactor` (Synthetic Workers) divides the run time, `synthPurchaseUnlocked` (Synthetic Procurement) opens an empty widget. Retention: `resleeveCarry.ts` (`recordLastLife`, `carryRetention`, called by `resetForResleeve`) and `ReflexArchive` (`reflexArchive.ts`, a `Steppable` the engine calls each slice after the automation: it buys back `lastLifePurchases` cheapest first through `Shop.canBuy` / `buy`). Tests share setup in `core/resleeveSkillsKit.ts`.

`ResleeveGate` (`resleeveGate.ts`) is the `ResleevePolicy`: re-sleeving needs the Unlock resleeving buyable (effect `unlockSleeveLevels`) and an empty lockout (`resleeveLockoutMs`, counted down in `GameEngine.advance`); `Progression` reads 0 sleeve levels until it is owned. The Re-sleeve button (`controls.ts`) is the purchase of that buyable until it is owned (`ViewModel.resleeveBuy`). In the UI, `ui/view/statReveal.ts` and `ui/view/sleeveGate.ts` decide what stays hidden. `Resleever` (`resleever.ts`) performs a re-sleeve on the live state: it writes the ending life down as a `SleeveRunRecord` (the network's own credits per second after the heat tax, and the total of the action levels), calls `resetForResleeve` (which keeps what the positive lists in `state.ts` name), appends the record to `GameState.runs` and, when the player owns the skill with the `synthSleeves` effect, gives a synthetic sleeve for it. `SynthSleeves` (`synthSleeves.ts`) answers how many sleeves there are and what they earn (`synthCreditsPerSecond`: the run's income times `min(1, current level total / recorded total)`); `NetworkSystem.payPassiveIncome` adds that income untaxed by heat. `Shop` calls a purchase listener after every purchase, which is how buying the skill gives the first sleeve. Re-sleeve points are derived like skill points (`Shop.pointsAvailable(state, currency)`: `runs.length x resleeve.pointsPerResleeve` minus the cost of the skills owned). Sleeve Euphoria (`euphoriaReduction`, `sleeveEuphoria.ts`) enters `Progression.actionXpReduction(state, actionId)`.

## Persistence
`serializeState`/`deserializeState` (versioned JSON, numbers as strings, defensive parsing; only the current format, version 6, is read: the game has not been released, so a save of another version is treated as unreadable and backed up). A scalar the save lacks keeps its fresh-game value, so adding a scalar to `fields.ts` needs no new version; changing the meaning of a field does, with a migration. Behind `SaveGame` on an injected `KeyValueStore` (`localStorage` in the browser). Autosave every 10 s, when the page is hidden and on `pagehide`. **One tab plays:** `main.ts` first calls `claimGame(navigator.locks)` (`app/tabGuard.ts`): the first tab takes a named Web Lock and keeps it until it closes; a later tab is told the game is taken and shows a notice BEFORE it loads the save, so the tab that was playing never stops. Without Web Locks the fallback `watchForOtherTab` (`storage` event) stops the tab that sees another tab write the save (there the tab that saves first wins).

Loading is defensive: the inventory keeps only known items and rarities with whole counts above 0 (a save without one loads empty, so no new version was needed; saving leaves used-up stacks out for the same reason, so save, load, save gives the same text), the Overclock and Focus switches keep only known actions that are switched on, a switch only where the action has bought its unlock (Overclock also needs an Overclock effect), Focus only up to the number of slots (base plus bought) (older saves without them load with both off), negative amounts become 0, non-finite times are dropped, the run counter is reduced modulo `runsPerSleeveXp`, copy counts are capped at a safe integer, and a buyable whose `requires` or `parents` are not owned is discarded. Each successfully loaded save is also copied to `cybersleeve.save.previous` (the last known-good save of a session start). A save that exists but cannot be read (corrupt, or from a newer version) is copied to `cybersleeve.save.unreadable` and the game falls back to the previous known-good save, so the next autosave cannot destroy progress. **Export and import** (`SaveGame.exportText` / `importText`, `app/saveTransfer.ts`): the player copies the save as text and can paste one back; a pasted save is validated, stored, and the page reloads (saving is switched off first so the running game cannot overwrite it). The temporary "Reset save" button calls `GameEngine.newGame()` (a full wipe, including sleeve XP) and `SaveGame.clear()` (removes the main and the previous save); it keeps the unreadable-save backup.

## Known limitations / next steps
- Scope decisions (2026-10-24): desktop browsers only for now (the PWA build still works, but mobile layout and install flow are out of scope); offline progress is deferred (the save has no timestamp yet); balance is not a factor yet, because most actions will get their own buyables later.
- `main.ts` is untested glue (excluded from the coverage report); everything it calls is tested (`throttle`, `tabGuard`, `debugControls`, the game loop, the render loop). Known gaps, decided not to fix yet: the 10-minute `maxDeltaMs` drops the time of a long-hidden tab (offline progress is a later mechanic; the drop is reported to `Diagnostics`, which `main.ts` prints in development builds and with `?debug`); `DerivedStats` recomputes sleeve stats and effects on every call outside a `Snapshot` scope (the screen opens one per refresh; the tick does not, and it is cheap: measured under 0.1 ms per step). Measured 2026-10-25 in headless Chrome: the whole game costs about 1% of a core; the visible "lag" was refresh cadence (about 8 Hz, uneven) and stepped bars, not computation.
- **Kill servers mechanics (units).** `DerivedStats` answers `startCostScale` (Decommission protocol and the chain on the start-cost share), `siphonSeconds`, `chainLinks` and `heatCoolingBlocked`; `ActionRunner` pays the scaled cost and the Credit Siphon at every start, keeps the chain (`GameState.chains`, added to the Overclock by an owned `overclockChain` buyable) in `extendChain` and breaks it when the action stops; `GameEngine.advance` skips `coolDownHeat` while `heatCoolingBlocked()`, and `BurnLeads` takes the same predicate. Admin keys reuse `ZeroDays` (one instance per item: `kind` selects `items.zeroDay` or `items.adminKey` and its toggle; the Admin key also rolls the Skill shard drop per batch); `SkillShards` uses a shard on a random unlocked action (`ActionState.skillShards`), and `LevelRule` takes a `delay` argument that `Progression.xpDelay` supplies for the action levels.
- **Number domains.** Amounts that multipliers can make unbounded are `BigNum`s (credits, nodes, ICE Rating, the two bonuses, XP). Heat, Legend and the cooldown timers are plain numbers because their effects saturate or are bounded. Multipliers derived from a `BigNum` (interface speed, node payout, the speed product) are plain doubles that SATURATE at the game's infinity (1e308) and treat NaN as 1, and a run never takes less than `engine.minRunDurationMs`; so a bonus beyond the double range cannot produce `Infinity`, a zero duration or NaN (`mathSafety.test.ts`).
- **Invariants and properties.** `testing/invariants.ts` lists what must hold for every reachable state (finite non-negative amounts, whole nodes, counters in range). `properties.test.ts` plays seeded random sequences of commands and ticks, on the test content and on the shipped content, and checks the invariants after every step (including that Overclock is on only where it is owned and no more actions are focused than there are slots; the "nodes are whole" check allows for the number type's precision: above about 1e8 it cannot hold every integer exactly), that saving and loading returns the same content, and that 30 s in one tick equals 30 ticks of 1 s.
- `runsTowardSleeveXp` (per action) is a plain JS number (exact up to 2^53 runs).
- Lint and format use Biome, because typescript-eslint does not support TypeScript 7 yet. Revisit if ESLint rules are needed.
- The HTML generator (`scripts/generate-docs.mjs`) parses the sources with the TypeScript compiler API, via a TypeScript 5 devDependency aliased as `typescript5` (TypeScript 7 has no JavaScript API; it is used for nothing else); curated sections (architecture, domain model, tick loop, runtime call graph, risks) live in `scripts/architecture.template.html` and must be edited by hand when the design changes.
