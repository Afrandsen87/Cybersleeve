## Layering (dependencies point downwards only)
```
main.ts ── ui/dom.ts ── ui/viewModel.ts
   │            │              │
   ▼            ▼              ▼
app/ (createGame, loop, persistence)  ──►  core/  ──►  numbers/ (BigNum interface)
                                     content/ (data)        │
                                                            ▼
                                              BreakInfinityNum (only file importing break_infinity.js)
```
- `numbers/` – `BigNum`/`NumberFactory` interfaces, the break_infinity.js adapter, `formatBigNum`.
- `core/` – pure game rules, no DOM, no timers, no storage. Time enters only via `GameEngine.tick(deltaMs)`. `GameEngine` is a thin facade over small units, none of which it builds itself (they are injected; `app/createGame.ts` is the one place that wires them): `DerivedStats` (all read-only calculations), `ActionRunner` (unlock rules, start costs, run progress, closed-form completion), `NetworkSystem` (passive income, growth), `cooldowns.ts` (heat and Infamy decay), `Progression`, `Shop`, `Economy` (formulas) and `OverflowPolicy`. The outside world depends only on narrow interfaces in `api.ts`: `GameQueries` (read-only; used by the view model; the union of `StateQueries`, `ActionQueries`, `SleeveQueries` and `ShopQueries`, so a consumer or a test fake can depend on just the part it reads) and `GameCommands` (what a player can do: `startAction`, `activateBuyable`, `augmentAction`, `giveUpForMoles`, `sellItems`, `resleeve`, `newGame`). Scalar state (credits, network, heat, ...) is described once as data in `fields.ts`; that table drives the initial state, re-sleeving, saving/loading and overflow repair. `rewards.ts` holds one descriptor per reward kind (the scalar it pays, whole units per run, whether `global.creditMultiplier` scales it, whether it may be paid per node); `effectTraits.ts` does the same for buyable effects (needs an action, can be switched on and off). Skills: `skills.ts` (`earnedSkillPoints`: 0 while all levels are 0, then 1 + floor(log10(total of action levels))); the `Shop` pays `skillPoints` purchases from `earned - cost of the skills owned` (nothing is stored), and `Progression` applies `actionXpReduction` to action levels the way it applies `sleeveXpReduction` to sleeve levels. Heat cooling with a skill speed and Moles is `coolHeatBoosted` (`heat.ts`, closed form; `moles` is a scalar of the state). Augments: `Augments` (`augments.ts`) applies one schematic from the inventory to an action (`GameEngine.augmentAction`), counted per rarity in `ActionState.augments` (`Record<rarityId, number>`); `DerivedStats.xpPerRun` multiplies the action XP by `augmentXpFactor` (additive within a rarity, `1 + n x bonus`, and the rarities multiply each other), and `ActionRunner` pays that, so batches stay closed-form. Items: `Inventory` (add drops, take and sell stacks) and `ItemDrops` (rolls what a batch of runs drops; the drop rules come from `DerivedStats.itemDrops`, i.e. from owned `itemDrop` buyables) with `sampling.ts` (`binomial`, `multinomial`, `RandomSource`). `diagnostics.ts` is the channel for "time had to be dropped" warnings. State is exposed only as a read-only `GameStateView` (`DeepReadonly<GameState>`, derived, never hand-copied).
- `content/` – `gameConfig.ts`: the single tuning file (actions, buyables, progression, speed, global levers, engine, runtime). See `docs/CONFIG.md`. Add content and retune here.
- `app/` – composition root (`createGame`), timer loop with injected `Scheduler`, `SpeedToggle` (x10 test fast-forward), `SaveGame` with injected `KeyValueStore` (`createBrowserStore` falls back to memory when `localStorage` is blocked), `createNewGameHandler` (the temporary "Reset save" button).
- `ui/` – `uiText` (every word the interface shows, as one table that is injected; names are placeholders), `viewModel` (pure, tested; stat widgets are lists of `StatRowView` and the Sleeve section layout is computed once per config) and `dom` (thin binding that builds stat widgets from those rows; covered by happy-dom tests). The corner test aids are shown only in development builds or with `?debug` in the address (`app/debugControls.ts`). `dom` only places what the view model says and sends commands; it holds no game rules (whether a click buys or switches an auto-run is `GameCommands.activateBuyable`). Every frame writes only what changed. **Render cost (2026-10-25):** the screen is drawn by `app/renderLoop.ts` on the display's frame clock (`requestAnimationFrame`, rate-limited by `runtime.renderMs`, skipped while the page is hidden); the game itself still steps on a timer. Hover texts are built only when shown: the view model exposes them as getters (`tip`, `speedTip`, `backChannelTip`; `StatRowView.hasTip` says whether a row has one), `dom.ts` registers them in a `TipRegistry` (`ui/tooltip.ts`) that writes the `data-tip` marker attribute once, and the tooltip box asks the registry on hover and re-reads the visible one after each refresh (no `MutationObserver`). Bars are full-width fills scaled with `transform: scaleX()` and a CSS transition of `--render-ms`; a bar that goes down snaps back instead of sliding. `buildViewModel` runs inside `engine.snapshot(...)` (`core/snapshot.ts`), in which the sleeve stats and skill points are computed once; `LevelRule` keeps its exact thresholds and its last level lookup. **Tabs (2026-10-25):** two centered tabs at the top, Character and Skills (`TabView`; the active tab is kept in the DOM layer only, not in the game state and not saved). Character holds the layout below; Skills holds a box with the skill buttons and the points available. The credits header sits above both panels. Desktop layout (changed 2026-10-25): a top band with the **Sleeve widget** (global stats + global buyables) on the left and, to its right, the Network widget beside **Sleeve Improvements** (the sleeve-wide purchases paid in credits: Rebuyable / One-time) and **Network Exploitation** (those paid in nodes), all three of equal width and equal height, with the Inventory widget under them (the band stretches so its widgets fill it without gaps); the purchases were moved out of the Sleeve widget; a line across the screen separates the band from the 3x2 grid of action cells below it (unused cells are empty placeholders).

## SOLID in practice
- **S** – `Progression` (XP/levels, including reduced sleeve XP requirements), `Shop` (purchases in credits or nodes), `effects` (buyable effects), `speed` (multiplier), `serialization`, `GameLoop`, `SaveGame` each have one job; `GameEngine` only orchestrates (see Layering).
- **O** – new speed factors = new `SpeedModifier`; new content = data in `gameConfig.ts`; a new scalar stat = one entry in `fields.ts` (plus the `GameState` field); a new reward kind = one entry in `REWARDS` (the compiler demands it); a new effect kind = a union member, one entry in `EFFECT_TRAITS`, one validator in `EFFECT_CHECKS` and a case in each resolver in `effects.ts` (the resolvers' `switch` statements end in `assertNever`, so a forgotten case does not compile). There is no global reward multiplier: a lever applies to one named kind of reward (today only `global.creditMultiplier`, for credits).
- **L** – anything satisfying `BigNum`, `Scheduler`, `KeyValueStore`, `ResleevePolicy`, `Tickable` is substitutable (tests use fakes).
- **I** – small interfaces (`Scheduler`, `Tickable`, `KeyValueStore`, `ResleevePolicy`).
- **D** – the engine receives its collaborators through the constructor; game code never imports break_infinity.js.

## Domain model
`GameState` = the scalars of `fields.ts` (credits, network (nodes), `iceRating`, `nodePayoutBonus` (credits per second added to the base value of a node by Push malware) and `hackingProficiency` as `BigNum`s because multipliers can make them unbounded; heat, `heatCooldownMs`, `infamy`, `infamyCooldownMs` and `networkRemainder` as plain numbers because their effects saturate or are bounded), `unlockedActions` (node-count unlocks that stay), `autoRunOff` (auto-run switches), per-action `{xp, sleeveXp, runsTowardSleeveXp, running, progressMs}`, copies owned per buyable (`purchased: Record<id, number>`), and the `inventory` (`Record<itemId, Record<rarityId, number>>`, whole counts as plain numbers capped at the largest exact integer). Items (`ItemDefinition`) and rarity tiers with their sell values (`RarityDefinition`) are content in `GameConfig.items`. Definitions (`ActionDefinition`, `BuyableDefinition`) are separate from state. Sleeve XP/level is per action. A buyable either belongs to one action (`BuyableDefinition.actionId`, displayed inside that action's card) or, with no `actionId`, to the sleeve (displayed in the Sleeve widget). Sleeve-wide effects (`interfaceSpeed`, `accessLevel`) are resolved by `resolveSleeveStats` into `SleeveStats` (access level, interface speed, heat), exposed as `GameEngine.sleeveStats()`; Interface speed is a `SpeedModifier` (a plain multiplier on every action's speed); heat is a tax on earned credits (`heatTaxFactor` with `sleeve.heatTaxPerPoint`, applied through `Economy` to run payouts and passive income) that cools down by `heatCooldownAmount` every `heatCooldownMs` while above 0 (`coolDownHeat` in `cooldowns.ts`, closed form so long ticks are cheap); access level gates actions (`ActionDefinition.requiredAccessLevel`, `GameEngine.isUnlocked`). An action's `rewardKind` decides whether a run pays credits or network nodes; nodes produce passive credits (`network.creditsPerNodePerSecond`).

### State lifetimes
| Field | Re-sleeve | New game |
|---|---|---|
| per action: sleeveXp, runsTowardSleeveXp (the positive list `CARRIED_OVER_ACTION_FIELDS`; nothing else survives; the applied `augments` do not) | kept | reset |
| credits (to `startingCredits`), network, action xp/progress, purchases (all copies), inventory | reset | reset |

## Tick loop
`setTimeout` (50 ms; keeps firing in background tabs) → `GameLoop.step` (real elapsed time × `timeScale`, capped at 10 min) → `GameEngine.tick(delta)` → the tick is cut into slices of at most `engine.maxSliceMs` (at most `engine.maxSlicesPerTick` slices); for each slice: passive network income (`nodes × rate × slice × heat-tax factor`, nodes owned at the start of the slice) → network growth → heat cooldown and Infamy decay (closed form) → for each action (skipped while locked by access level): apply auto-run, advance progress, then complete runs **in batches** (below) → `OverflowPolicy.apply` → `render()` (skipped while `document.hidden`). A step that throws is reported (`onError`, default `console.error`) and the loop carries on.
**Progress of a run.** `ActionState.progress` is the share (0 up to, not including, 1) of the current run that is done. Each step takes `(1 - progress) x duration` to finish at the speed of the moment, so a change of speed only changes the rest of the run. A tolerance of `1e-9` of a run (`PROGRESS_EPSILON` in `actionRunner.ts`) stops floating-point rounding from keeping a finished run waiting. The save format is version 4; version 3 stored the progress in milliseconds and is still read, its run starting again.

**Batches (closed form).** All runs between two level changes are identical in speed and reward, so they are applied at once: `n = min(runs that fit in the time left, Progression.runsBeforeLevelChange)`. A batch pays its reward in full (`n × reward`; heat taxes only the credits network nodes produce, so a run's payout does not fall as heat rises), adds `n × heat`, and records `n × XP` and `n` counted runs. A tick therefore costs about one batch per level gained, not one iteration per run; `maxBatchesPerTick` is only a safety net. A manual run that completes drops leftover time; an auto-run carries it into the next batch.

**Item drops.** Chance cannot be rolled run by run when a batch holds millions of runs, so `ItemDrops.roll(action, n)` draws the number of drops directly from Binomial(n, chance) and splits them over the rarities with a multinomial draw (`sampling.ts`: exact up to 1000 runs, Poisson or normal approximation above). A batch of any size costs the same. The randomness is an injected `RandomSource` (`Math.random` in `createGame`, a seeded one in tests). Rules are read when the runs complete, so a rule that changes over time applies to later runs. `DerivedStats.itemDrops` hands out the rules with their weights as they stand now: a `rarityShiftFromProficiency` buyable shifts them with `shiftWeights` (`rarityShift.ts`), one step per whole order of magnitude of Hacking Proficiency. One long tick and many short ones give the same drop rate, not the same drops (it is random); `items.test.ts` checks the rate.

**Tick granularity and slicing.** Within a slice passive income and heat cooling use the nodes and heat at the start of the slice, and heat added by runs starts cooling in the next slice. Systems that feed back on themselves (interface speed rising with every run, heat cooling while the network pays) would drift if a long tick were computed in one go, so a tick longer than `engine.maxSliceMs` is cut into slices that run one after another. Result: one long tick and many short ones agree (`batching.test.ts` checks interface speed within 2% over 5 minutes and passive income under cooling within 1% over 50 minutes, and that without slicing the first would be clearly off). The cost of a tick is bounded by `engine.maxSlicesPerTick`; beyond that the slices simply get longer and the agreement degrades gracefully. Runs of actions with a start cost still complete one per batch (a share-of-balance cost has no exact closed form because of rounding), so `maxBatchesPerTick` caps them per slice.

## Number handling (replaces the reference game's workarounds)
All amounts are `BigNum` (mantissa/exponent). The adapter treats exponent ≥ 9e15 (library saturation) as non-finite, so overflow is detectable. No iteration over huge counts (runs are batched, see Tick loop), no rounding hacks. After every slice the `OverflowPolicy` repairs non-finite scalars and XP; the default clamps overflow to `NumberFactory.maxValue()` (the largest safe integer for plain-number scalars) and turns negative overflow and **NaN into 0** (NaN is a bug upstream and must never become a windfall) so the state stays valid and saveable. The real reaction, the "infinity" prestige, is not designed yet. Level calculation uses `floorLog10`, exact at powers of ten and valid beyond the double range (tested up to 1e1000).

## Persistence
`serializeState`/`deserializeState` (versioned JSON, numbers as strings, defensive parsing; only the current format, v3, is read: the game has not been released, so a save of another version is treated as unreadable and backed up). A scalar the save lacks keeps its fresh-game value, so adding a scalar to `fields.ts` needs no new version; changing the meaning of a field does, with a migration. Behind `SaveGame` on an injected `KeyValueStore` (`localStorage` in the browser). Autosave every 10 s, when the page is hidden and on `pagehide`. A tab that sees another tab write the save (`storage` event, `app/tabGuard.ts`) stops playing and saving and shows a notice, so two tabs cannot overwrite each other.

Loading is defensive: the inventory keeps only known items and rarities with whole counts above 0 (a save without one loads empty, so no new version was needed), negative amounts become 0, non-finite times are dropped, the run counter is reduced modulo `runsPerSleeveXp`, copy counts are capped at a safe integer, and a buyable whose `requires` are not owned is discarded. A save that exists but cannot be read (corrupt, or from a newer version) is copied to `cybersleeve.save.unreadable` before the game starts over, so the next autosave cannot destroy it. The temporary "Reset save" button calls `GameEngine.newGame()` (a full wipe, including sleeve XP) and `SaveGame.clear()`; it keeps that backup.

## Known limitations / next steps
- Scope decisions (2026-10-24): desktop browsers only for now (the PWA build still works, but mobile layout and install flow are out of scope); offline progress is deferred (the save has no timestamp yet); balance is not a factor yet, because most actions will get their own buyables later.
- `main.ts` is untested glue (excluded from the coverage report); everything it calls is tested (`throttle`, `tabGuard`, `debugControls`, the game loop, the render loop). Known gaps, decided not to fix yet: the 10-minute `maxDeltaMs` drops the time of a long-hidden tab (offline progress is a later mechanic; the drop is reported to `Diagnostics`, which `main.ts` prints in development builds and with `?debug`); `DerivedStats` recomputes sleeve stats and effects on every call outside a `Snapshot` scope (the screen opens one per refresh; the tick does not, and it is cheap: measured under 0.1 ms per step). Measured 2026-10-25 in headless Chrome: the whole game costs about 1% of a core; the visible "lag" was refresh cadence (about 8 Hz, uneven) and stepped bars, not computation.
- **Number domains.** Amounts that multipliers can make unbounded are `BigNum`s (credits, nodes, ICE Rating, the two bonuses, XP). Heat, Infamy and the cooldown timers are plain numbers because their effects saturate or are bounded. Multipliers derived from a `BigNum` (interface speed, node payout, the speed product) are plain doubles that SATURATE at the largest double and treat NaN as 1, and a run never takes less than `engine.minRunDurationMs`; so a bonus beyond the double range cannot produce `Infinity`, a zero duration or NaN (`mathSafety.test.ts`).
- **Invariants and properties.** `testing/invariants.ts` lists what must hold for every reachable state (finite non-negative amounts, whole nodes, counters in range). `properties.test.ts` plays seeded random sequences of commands and ticks, on the test content and on the shipped content, and checks the invariants after every step, that saving and loading returns the same content, and that 30 s in one tick equals 30 ticks of 1 s.
- `runsTowardSleeveXp` (per action) is a plain JS number (exact up to 2^53 runs).
- Lint and format use Biome, because typescript-eslint does not support TypeScript 7 yet. Revisit if ESLint rules are needed.
- The HTML generator (`scripts/generate-docs.mjs`) parses the sources with the TypeScript compiler API, via a TypeScript 5 devDependency aliased as `typescript5` (TypeScript 7 has no JavaScript API; it is used for nothing else); curated sections (architecture, domain model, tick loop, runtime call graph, risks) live in `scripts/architecture.template.html` and must be edited by hand when the design changes.
