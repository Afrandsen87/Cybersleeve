# Layering notes (to be redistributed)

The layering diagram and the long per-folder notes that were in ARCHITECTURE.md. Each context migration step (docs/review/execution-plan.md S3-S10) moves its own sentences from the `core/` bullet into that context's doc; the diagram stays here until the last step.

### Layering (dependencies point downwards only)
```
main.ts ── ui/dom.ts ── ui/viewModel.ts
              │              │
       ui/widgets/*    ui/view/*   (one file per widget / per view)
   │            │              │
   ▼            ▼              ▼
app/ (createGame, loop, persistence)  ──►  core/  ──►  numbers/ (BigNum interface)
                                     content/ (data)        │
                                                            ▼
                                              BreakInfinityNum (only file importing break_infinity.js)
```
- `numbers/` – `BigNum`/`NumberFactory` interfaces, the break_infinity.js adapter, `formatBigNum`.
- `core/` – pure game rules, no DOM, no timers, no storage. Time enters only via `GameEngine.tick(deltaMs)`. The heat skills are split by responsibility: `heatEffects.ts` (their registry entries, spread into `EFFECTS`), `heatPace.ts` (the pure cooling pace: idle factor, Mole aggregation) and `heat.ts` (tax and cooldown maths, including the tax cap). `GameEngine` is a thin facade over small units, none of which it builds itself (they are injected; `app/createGame.ts` is the one place that wires them): `DerivedStats` (all read-only calculations), `ActionRunner` (access gating, start costs, run progress, closed-form completion), `NetworkSystem` (passive income, growth), `cooldowns.ts` (heat and Legend decay), `Progression`, `Shop`, `Economy` (formulas) and `OverflowPolicy`. The outside world depends only on narrow interfaces in `api.ts`: `GameQueries` (read-only; used by the view model; the union of `StateQueries`, `ActionQueries`, `SleeveQueries` and `ShopQueries`, so a consumer or a test fake can depend on just the part it reads) and `GameCommands` (what a player can do: `startAction`, `activateBuyable`, `augmentAction`, `giveUpForMoles`, `sellItems`, `resleeve`, `newGame`). Scalar state (credits, network, heat, ...) is described once as data in `fields.ts`; that table drives the initial state, re-sleeving, saving/loading and overflow repair. `rewards.ts` holds one descriptor per reward kind (the scalar it pays, whole units per run, whether `global.creditMultiplier` scales it, whether it may be paid per node); `effectRegistry.ts` is the registry of buyable effects: ONE entry per effect kind holding its traits (needs an action, can be switched on and off), its validator and the hooks that add it to an action or to the sleeve; `effects.ts` loops over the owned buyables and calls those hooks, so it has no `switch` over kinds, and `effectTraits.ts` is a view of the registry plus `assertNever`. `infinity.ts` defines the game's infinity, 1e308, which the overflow policy and every saturating multiplier use. `backChannel.ts` (`BackChannel`) turns items into Moles, `Shop.toggle` switches auto-runs, so the engine mutates no state itself. Skill trees: `ui/view/skillTree.ts` (`buildSkillLanes`, pure) puts the skills (and the re-sleeve skills) in lanes by `branch`, places each on a grid (column = depth through `parents`; rows come from the tree of first parents: each childless skill takes the next free row, so every path is its own lane, and a parent is centred on its children, possibly on a half row) and decides which are readable (own `requires` owned and every parent readable; the rest are masked as `???`); `ui/widgets/skillTree.ts` (`mountSkillTree`) draws a tree once, sideways, with CSS variables `--col`/`--row` and SVG edges in grid units, and a refresh only toggles classes and text. Content: one file per branch in `content/buyables/skillBranches/`. Skills: `skills.ts` (`earnedSkillPoints`: 0 while all levels are 0, then 1 + floor(log10(total of action levels))); the `Shop` pays `skillPoints` purchases from `earned - cost of the skills owned` (nothing is stored), and `Progression` applies `actionXpReduction` to action levels the way it applies `sleeveXpReduction` to sleeve levels. Heat cooling with a skill speed and Moles is `coolHeatBoosted` (`heat.ts`, closed form; `moles` is a scalar of the state). Augments: `Augments` (`augments.ts`) applies one schematic from the inventory to an action (`GameEngine.augmentAction`), counted per rarity in `ActionState.augments` (`Record<rarityId, number>`); `DerivedStats.xpPerRun` multiplies the action XP by `augmentXpFactor` (additive within a rarity, `1 + n x bonus`, and the rarities multiply each other), and `ActionRunner` pays that, so batches stay closed-form. Items: `Inventory` (add drops, take and sell stacks) and `ItemDrops` (rolls what a batch of runs drops; the drop rules come from `DerivedStats.itemDrops`, i.e. from owned `itemDrop` buyables) with `sampling.ts` (`binomial`, `multinomial`, `RandomSource`). Overclock and Focus: four effect kinds, two per action (`overclockUnlock`, `focusUnlock`: action hooks that set `ActionEffects.overclockUnlocked` / `focusUnlocked`) and two sleeve-wide (`overclockStrength`: `SleeveStats.overclockStrength = 1 + perCopy x copies`; `focusSlots`: `SleeveStats.extraFocusSlots`, added to `focus.baseSlots`; what Focus gives is the `focus` section of the configuration) and two flag maps in the state (`overclocked`, `focused`, per action id, off at first, reset by re-sleeving, saved and sanitised on load against what is owned). `DerivedStats.overclockStatus` / `focusStatus` say what each is for an action (they return `null` until the action has bought the unlock, so there is no switch to show); they feed two extra `SpeedModifier`s (`overclock`, `focus`, factor `1 + bonus`, 1 while off) through `SpeedContext`, so the speed stays one product. An action's `OverclockRule` is a mix of gains (`speedBonus`, `rewardBonus`: scaled by the strength) and fixed costs and extras (`heatPerMinute`, `heatPerRunFactor`, `completionEffects`, `alsoPays`), so each action can have its own; `OverclockStatus` carries the resolved values, `DerivedStats.activeOverclock` is the status while the switch is on, `DerivedStats.rewardMultiplier` includes `1 + rewardBonus`, and `ActionRunner.completeRuns` draws how many runs of the batch make heat (`heatChance` x Overclock `heatChanceFactor`, one `binomial` draw per batch with the injected `RandomSource`; no draw at a chance of 1), applies the heat factor, the completion effects and `payAlso` (the other action's reward for the same number of runs) in closed form. `ActionToggles` (`actionToggles.ts`) switches them (`GameEngine.toggleOverclock` / `toggleFocus`; Focus needs a free slot). The heat Overclock costs is charged by `ActionRunner.tick` for the time `advance` reports the action ran, so it is closed form and tick size does not matter. `ZeroDays` (`zeroDays.ts`, configured by `items.zeroDay`, toggle in `GameState.zeroDaysOn`) holds the Zero-day toggle (`GameEngine.toggleZeroDays`) and settles a batch of completed runs in `ActionRunner.completeRuns`: `claim` takes `min(runs, held)` Zero-days from the inventory and those runs are critical for sure, the rest roll the normal chance (`CriticalSuccesses`); the toggle switches itself off at 0 held, and is saved (read back as off when none is held). `CriticalLinks` (`criticalLinks.ts`) keeps the bank of guaranteed critical successes (`GameState.bankedCriticals`): a `criticalLink` buyable (Ransomware) makes each critical run of its action `bank` one for a target action, and the target's next completed runs `claim` them (`min(runs, banked)`, closed form) before Zero-days and the critical chance are considered. `criticalBoost` (Persistence) multiplies the critical rule in `DerivedStats.criticalRule`; `overclockHeatFactor` (Obfuscation) lowers `OverclockStatus.heatPerRunFactor` through `SleeveStats.overclockHeatFactors`. `BurnLeads` (`burnLeads.ts`) uses one Burn lead from the inventory (`GameEngine.useBurnLead`; configured by `items.burnLead`): it takes `heatFraction` of the current heat away. Heat is a plain number that may hold fractions; `coolHeat` / `coolHeatBoosted` (`heat.ts`) remove it in whole points only (a small epsilon absorbs floating-point dust) and the cycle bar waits while there is less than one point. `diagnostics.ts` is the channel for "time had to be dropped" warnings. State is exposed only as a read-only `GameStateView` (`DeepReadonly<GameState>`, derived, never hand-copied).
- `content/` – `gameConfig.ts`: the single tuning file (actions, buyables, progression, speed, global levers, engine, runtime). See `docs/CONFIG.md`. Add content and retune here.
- `app/` – composition root (`createGame`), timer loop with injected `Scheduler`, `SpeedToggle` (x10 test fast-forward), `SaveGame` with injected `KeyValueStore` (`createBrowserStore` falls back to memory when `localStorage` is blocked), `createNewGameHandler` (the temporary "Reset save" button).
- `ui/` – **Inventory (2026-10-26):** the tip of every row lists where its stack drops from (`DerivedStats.dropSources`, exposed as `GameQueries.dropSources`: per action that can drop it, the chance of one completed run, computed from `itemDrops` so chance multipliers and rarity shifts are included). `InventoryView.rows` has a row for every item and rarity (`InventoryRowView`: label, `symbol` fallback, `rarityIndex`, count, `sellable`, `usable`, `canUse`, `backChannel`, tip); `dom.ts` draws them as tiles (`buildInventoryWidget` / `renderInventory`): kept or used items in one section, sellable ones in a section to the right whose tiles are selected by clicking (`InventoryWidget.selected`, a choice of the screen only) and acted on by the Sell, Sell all and Back channel buttons beside the grid; clicking a usable tile (Burn lead) calls `GameCommands.useBurnLead`. **Icons (2026-10-25):** the pixel art is data in `content/icons.ts` (16x16 grids of characters, a palette, and `ENTITY_ICONS`, which says which icon an action, item or the credits shows). `ui/pixelIcon.ts` (pure, tested) turns the grids into SVG data URLs once at start-up (`createIconSource`); `dom.ts` takes the lookup as `MountOptions.icons` (default: none) and gives the element a `has-icon` class and a `--icon` custom property, which `style.css` paints in a `::before` box, so replacing an element's text never removes its icon. New icon: add a grid and a line in `ENTITY_ICONS`; the content test fails when an action, item or the credits has none. `uiText` (every word the interface shows, as one table that is injected; names are placeholders), `viewModel` (pure, tested; stat widgets are lists of `StatRowView` and the Sleeve section layout is computed once per config) and `dom` (thin binding that builds stat widgets from those rows; covered by happy-dom tests). The test aids bar (a bar at the top of the page, in the layout flow so it never covers the tabs) is shown only in development builds or with `?debug` in the address (`app/debugControls.ts`). `dom` only places what the view model says and sends commands; it holds no game rules (whether a click buys or switches an auto-run is `GameCommands.activateBuyable`). Every frame writes only what changed. **Render cost (2026-10-25):** the screen is drawn by `app/renderLoop.ts` on the display's frame clock (`requestAnimationFrame`, rate-limited by `runtime.renderMs`, skipped while the page is hidden); the game itself still steps on a timer. **The square (2026-10-26):** each action card has a square beside its reward line and its two level bars, under the full-width run bar (`ActionView.square`, an `ActionSquareView` of four `SquareCellView`s: Auto-run, Overclock, Focus, Augment). While Auto-run is not owned the whole square is one button that buys it; afterwards it is a 2x2 grid in which a cell is a purchase (`mode: 'buy'`, the unlock buyable), a toggle (`'toggle'`), the Augment press (`'press'`) or an empty placeholder (`'empty'`). The view model flags the buyables that live in the square (`BuyableView.inSquare`: effect kinds `autoRun`, `overclockUnlock`, `focusUnlock`) so `dom.ts` leaves them out of the row of purchases; `dom.ts` builds both the big button and the grid once (`buildSquare`) and `renderSquare` shows one of them and updates the cells from the view. Hover texts are built only when shown: the view model exposes them as getters (`tip`, `speedTip`, `backChannelTip`; `StatRowView.hasTip` says whether a row has one), `dom.ts` registers them in a `TipRegistry` (`ui/tooltip.ts`) that writes the `data-tip` marker attribute once, and the tooltip box asks the registry on hover and re-reads the visible one after each refresh (no `MutationObserver`). Bars are full-width fills scaled with `transform: scaleX()` and a CSS transition of `--render-ms`; a bar that goes down snaps back instead of sliding. `buildViewModel` runs inside `engine.snapshot(...)` (`core/kernel/snapshot.ts`), in which the sleeve stats and skill points are computed once; `LevelRule` keeps its exact thresholds and its last level lookup. **Tabs (2026-10-25):** two centered tabs at the top, Character and Skills (`TabView`; the active tab is kept in the DOM layer only, not in the game state and not saved). Character holds the layout below; Skills holds a box with the skill buttons and the points available. The credits header sits above both panels. Desktop layout (changed 2026-10-25): a top band with the **Sleeve widget** (global stats + global buyables) on the left and, to its right, the Network widget beside **Sleeve Improvements** (the sleeve-wide purchases paid in credits: Rebuyable / One-time) and **Network Exploitation** (those paid in nodes), all three of equal width and equal height, with the Inventory widget under them (the band stretches so its widgets fill it without gaps); the purchases were moved out of the Sleeve widget; a line across the screen separates the band from the 3x2 grid of action cells below it (unused cells are empty placeholders).
