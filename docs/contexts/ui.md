## Firmware tab presentation (2026-10-31)

- `view/firmwareNodeState.ts` owns `nodeState`: installed > encrypted > locked > affordable > available, shared with Automation. The widget maps that view state to a class rather than deriving affordability or gating.
- `view/firmwareInspector.ts` owns `buildInspectorView` and `defaultSelection`: first affordable node, otherwise the first branch's root. It reads existing node views and formatted balances; it never computes prices, effects or affordability. Encrypted nodes expose only `???`, their state and the generic reveal hint, with no icon, cost or relation-name leaks.
- `view/firmwareBranches.ts` owns `branchSummary`: installed nodes over all nodes, including encrypted places already shown by the tree reveal exception. Purpose is hidden while every node is encrypted. Purpose lines are approved mockup placeholders in `ui/firmwareText.ts`, exposed as `uiText.firmware`.
- `widgets/skillsPanel.ts` coordinates the two-column layout, current pool readouts, encrypted-state legend and inspector. `UiSelection.firmwareSelected` pins a node in UI memory only; widget-local hover previews return to that selection or the default on tree exit. A Firmware node click selects; `widgets/firmwareInspector.ts` calls `ctx.activate` once and `ctx.refresh` on INSTALL. Automation keeps node-click activation.
- Drawing cost: while the Firmware tab is hidden its panel draws nothing and drops a hover in progress (`openTab` in `testing/domMountKit.ts` shows it in full-UI tests). While shown, the trees report whether a node state or owned count moved and the inspector is rebuilt only then, or when the points change.
- `view/skillTreePaths.ts` owns loop-safe all-parent `pathToRoot` and `childrenOf`. `widgets/skillTreeEdges.ts` owns SVG geometry and node/edge hover classes, updated per hover rather than per frame. `widgets/skillTree.ts` detects ownership increases between renders and adds CSS install/flow classes, removed on animation completion; first render never animates an existing installation.
- `styles/firmware.css` owns cards, inspector and legend; `styles/skills.css` retains shared node-state visuals, geometry and branch colours. Main cards use 38 px nodes, 54 px columns and 50 px rows, supplied once by widget geometry to CSS and SVG. Automation retains its spacing. `styles/panels.css` supplies shared `.panel` chrome; reduced motion disables pulse, static and install feedback.
- Reveal checklist: readouts follow the existing tab/pool visibility; legend appears only while a displayed node is encrypted; branch purposes wait for a readable node; encrypted inspection reveals no content. Sleeve Firmware remains subject to the existing first-re-sleeve and parent gates. Persistence wording was verified against `CARRIED_OVER_BUYABLE_CURRENCIES` and the currency descriptor's `carriedOverResleeve` flag.
- Impact and layer readiness: UI only, with the current sleeve's point pools and existing currency words; no mechanics, save fields, tuning, global singleton, copy iteration or assumption about additional corporations/prestige layers is added.

## Main screen view (2026-10-31)

- **Panel precision:** panel stat values keep `PANEL_DIGITS` (4) significant figures through `formatSignificant` (`numbers/format.ts`; from 1000 it hands over to the `formatBigNum` suffixes). Tooltips keep full precision.
- **HUD** (`view/hudView.ts`, `ViewModel.hud`): the credits readout, the income rate from `SleeveQueries.creditsPerSecond` (owner: `NetworkSystem.creditsPerSecond`), first shown when it is above 0 and then kept through the reveal ledger (`stat:incomeRate`). The top bar has no heat gauge (removed 2026-10-31 by the user: the Sleeve panel shows heat).
- **Tabs:** `TabView.count` carries the skill or automation points (`null` at 0); the label holds no count.
- **Sleeve groups** (`view/sleeveGroups.ts`): a table puts every sleeve stat row in ACCESS, SKILL, DEFENSE (ICE Rating, Legend) or RISK (heat); a group is hidden when all its rows are. The Legend decay bar is hidden while Legend is 0 (`StatBarView.hidden`).
- **Heat gauge:** `SleeveView.heatGauge` (`null` while the heat row is hidden) places heat on a strip from `view/heatStrip.ts` (`heatStripLayout`, the one owner of strip positions, also meant for the Auto Burn panel: span `1.5 x` the largest of the tax start and markers, heat beyond pinned with `overflow`). The tax zone starts at `heatStopPoint`; with a capped tax there is no zone and the legend names the cap. While heat cools the heat bar's label is the cycle (`-amount / seconds`, seconds from `cycleSeconds` in `heat/heatModel.ts`, the one owner the heat tip also reads).
- **Network:** `NetworkView.taxNote` (red, the share from `creditKeepFactor` only, `null` at no tax or with no nodes) and `status` (`LINKED` while there are nodes). Main screen wording is `uiText.mainScreen` (`ui/hudText.ts`).

### Look of the main screen (presentation, 2026-10-31)

- **Colour language:** one meaning per colour, listed in the comment at the top of `ui/style.css` (`--info` on/information, `--run` running, `--heat`, `--danger` loss, `--gain`, `--auto`, `--afford`); numbers and data values use `--mono`. `--cyan` and `--magenta` are aliases of `--info` and `--run`.
- **Panel chrome** (`styles/panels.css`): notched corners (`clip-path`), bracket accents, a faint page grid and a fixed scanline overlay. Headers are built by `widgets/panelHeader.ts` (`.ph`: `// TITLE` drawn by CSS, status LED hidden for `null`). `.led` and `.led-dot` are shared, coloured through `--c`.
- **Style folder:** `ui/style.css` is the base; area files live in `ui/styles/` (list in `docs/ARCHITECTURE.md`).
- **Widgets only draw view fields:** `widgets/hud.ts` (credits, rate, tabs), `widgets/tabBar.ts` (badge from `TabView.count`, colour by `data-tab` in CSS), `widgets/heatGauge.ts` (fill by `transform`, tax zone from `strip.taxStartPercent`), `widgets/statWidget.ts` (group headers, hidden bars, `StatRowView.tone` as `data-tone`). `networkView` sets the tone (income gain, a taxed +0 danger, nodes info). The re-sleeve box title is `SleeveView.resleeveTitle`.

## Reveal ledger and tab blink

**Reveal ledger** (`wallet.revealed`, `economy/revealLedger.ts`): a set of typed keys `stat:<id>`, `tab:<id>`, `skill:<id>`, `buyable:<id>` for everything the player has ever been shown. Only grows; survives a re-sleeve (`CARRIED_OVER_WALLET_FIELDS`). Queries never write it: each view build uses one `RevealTracker` (`ui/view/revealTracker.ts`) that says "shown" when the key is noted or the natural rule says so now, and collects keys that are new into `ViewModel.newlyRevealed`; `ui/dom.ts` then calls the engine command `noteRevealed(keys)` only when that list is not empty. Unknown and repeated keys are ignored (ids are resolved against the content, not a branch). Tabs: `tabsView` takes the tracker and a `TabAttention` (held by `ui/dom.ts` in `UiSelection`); `BuyableView.gated` marks a remembered purchase whose requirements are unmet (class `gated`, greyed).

The autosale branch uses the existing first-parent placeNodes layout: slot 3 has children 4 and 7 on separate rows. No extra branch or layout algorithm is needed. Autosale and auto Back Channel switches are individually hidden until their rarity permission is owned. The tree keeps all icons visible and masks text/tips through manual-concept prerequisites. Back Channel controls occupy a second row and hide while manual Back Channel is absent; lazy skill tips use the existing getter path. Once dispersal slot 1 is owned, its controls show unlocked actions as toggles, a selected / available slots count, and only known allowed rarity names. A full selection disables further ticks while selected targets stay untickable. Percentage inputs and Share (%) text are removed. Dispersal skill text waits for the schematic concept and each rarity reveal; icons remain unique and visible.

## Decisions (from docs/DECISIONS.md)


*Group: Decided 2026-10-24 (by the user)*
- **UI:** **vanilla TypeScript** with a small own view layer. Core game logic is framework-free and has no DOM access; views are thin and data-driven.

*Group: Decided 2026-10-25 (by the user, after the second review)*
- All interface wording lives in `src/ui/uiText.ts`; `viewModel.ts` and `dom.ts` hold none. Stat widgets are data-driven rows (`StatRowView`), not hand-written per field.

*Group: Decided 2026-10-25 (by the user, after the second review)*
- The test aids (Reset save, Speed x10) are shown only in development builds or with `?debug` in the address.

*Group: Decided 2026-10-25 (by the user, after the performance review)*
- **Rendering rules.** The screen is drawn by `RenderLoop` on `requestAnimationFrame` (rate-limited by `runtime.renderMs`); the game steps on its own timer. Bars move with `transform: scaleX()` plus a CSS transition of `--render-ms`, never by `width`. Hover texts are built only when shown: view-model tips are getters, `dom.ts` registers them in a `TipRegistry`, and nothing reads them every frame. `buildViewModel` runs inside `engine.snapshot(...)`. Measure before optimising: the game cost about 1% of a core when measured, so new UI work should keep it that way (no per-frame work that scales with the number of buyables beyond what the view model already does).

*Group: Decided 2026-10-26 (by the user, Overclock, Focus and Burn leads)*
- **The square (2026-10-26):** on every action card the run bar spans the full width, and under it a square (the same height as the reward line plus the two level bars) sits beside those. Before Auto-run is bought the whole square is the button that buys it; afterwards it is a 2x2 grid of Auto-run, Overclock, Focus and Augment. A cell whose unlock is not bought is a purchase button, a bought one is a toggle, and a feature the action does not have is an empty dashed cell. These buyables (effect kinds `autoRun`, `overclockUnlock`, `focusUnlock`) are not shown in the card's row of purchases (`BuyableView.inSquare`).

*Group: Decided 2026-10-25 (by the user, icons)*
- **Pixel-art icons**, 16x16, drawn as text grids in `content/icons.ts` and assigned to entities by id (`ENTITY_ICONS`); nothing in `core` knows about them. Style: limited neon palette on dark, drawn crisp (`image-rendering: pixelated`). Current set: network (Grow network), terminal (Practice Hacking), bug (Push malware), server rack (Kill servers), grinning skull (Build Legend), redacted file (Kompromat), chip (Augment schematic), flame (Burn lead), a chip with a stylised C (credits: in the universe credits are held on chips). Shown on action titles, inventory rows and the credits line; buyables, skills and Moles have none yet.

*Group: Decided 2026-10-25 (by the user, icons)*
- **Inventory layout (2026-10-26):** a grid of tiles, one for every possible item and rarity (icon, count underneath, dimmed when 0). Items that cannot be sold are in a section on the left; sellable ones in their own section on the right, where a tile is selected by clicking and sold with the Sell and Sell all buttons beside the grid. Clicking a Burn lead tile uses one. The Back channel (Kompromat for Moles) is a third button beside Sell and Sell all, for the selected common Kompromat.

*Group: Decided 2026-10-26 (by the user, after the full review)*
- **The Re-sleeve button is the Sleeve levels purchase (2026-10-27):** one button at the bottom of the Sleeve widget (`ui/widgets/controls.ts`, `buildResleeveRow`). Until the unlock is owned it shows the buyable (name and price, `ViewModel.resleeveBuy`) and a click buys it through `UiContext.activate`; once owned it is the two-click Re-sleeve action, disabled for the lockout. The buyable is left out of the Sleeve Improvements list (`sectionLayout`, `sleeveView`). **Changed 2026-10-30 (by the user):** the button shows once Sleeve levels is owned and is the purchase of Unlock resleeving (not Sleeve levels) until that is bought; Sleeve levels is listed with the other purchases. Every skill tree is always visible in the Skills tab, and the re-sleeve trees show after the first re-sleeve point (the Anonymity texts wait for heat: `branchMask.ts`).

*Group: Decided 2026-10-30 (by the user)*
- **The Re-sleeve row sits at the bottom of the Sleeve widget whatever its height:** the widget is a flex column and the row has `margin-top: auto` (at least 12px from the content above). CSS only (`style.css`).
- **Action cards show their reward area as two lines of the same size** (decided 2026-10-30, by the user): a gains line (`ActionView.rewardLine`: what a run pays or teaches) and a costs line (`ActionView.costLine`, from `costItems` built by `ui/view/actionCosts.ts`: heat chance and amount, heat per second, start cost, and while Overclock is on its heat per minute, nodes per run and "prevents heat cooldown while active" when its rule stops heat cooling). Values come from their owners (`GameQueries.heatChance` -> `ToggleStats.heatChance`, which the run batch also draws with; `startCostOf`; `overclockStatus`) and are only formatted. The costs line is always drawn, empty for an action with no costs, so every card lines up. The start cost left the info line.
- **Fast run bars:** when an action's current run duration (`ActionView.durationMs`, from `currentDurationMs`) is under `FAST_BAR_MS` (200 ms, a display policy in `ui/view/fastBar.ts`, not game tuning) the bar is drawn full while the action runs or auto-runs, and while Auto-run is on the number of runs per second (`1000 / durationMs`) is written on it (`uiText.perSecond`). A single manual run has no rate.
- **XP bar tooltips:** hovering the level XP or the sleeve XP bar of an action card shows how much XP a run gives (base XP x XP lever x Augment factor x Neural Mirror factor, each line only while its factor is not 1; the critical XP multiplier once a critical run is possible; for sleeve XP the runs per grant and the XP per grant) and the cost of the next level (first level x growth ^ (level - delay) x (1 - reduction), delay and reduction only when they apply). The figures come from `xpPerRunBreakdown`, `actionXpCurve`, `sleeveXpCurve`, `sleeveXpGrant` and the level queries (`ui/view/xpTipView.ts` builds the parts, `ui/tipTextXp.ts` the words); the sleeve bar tip exists only once sleeve levels are unlocked.
- **Toggle cells and tip details** (2026-10-30): an untoggled Auto-run, Overclock or Focus cell (both Focus halves) keeps the teal owned look, a toggled one also glows magenta (`.square > .upgrade.owned.on`, `.cell-half.on`); masked skill nodes dim to 0.35 like locked ones. Auto Burn protocol conditions show the live Floor and Redline from `AutoBurnRules` (`autoBurnView`). The Decommission protocol start cost text shows the live share from `startShareOf`. The Hardened payload tip reads "ICE Rating per level = base + Forensic hardening Y = Z" (Y from `hardeningBonusPerLevel`; the Forensic term is hidden until it is owned). The synthetic sleeves tip adds "Scales to" from `synthIncomeCeiling`.

- **Purchase look (2026-10-31, by the user):** one state set for every purchase button and action-card cell, always glowing in its border colour. First copy affordable: blue border, glow, full-colour icon. Repeatable and bought: blue border, dimmed icon; teal glow and full icon while another copy is affordable. Unbought and unaffordable: grey and dim. `maxed` (no more copies, or a bought toggle cell): no border, full-colour icon, unlit; a toggle cell that is on glows gold with a gold border. Classes: `purchasable`, `owned`, `maxed`, `on` (`widgets/upgradeButtons.ts`, `widgets/actionCards.ts`, `style.css`); skill nodes keep their lane colours.

- **Main screen redesign, Batch A (2026-10-31, by the user, approved mockup `docs/mockups/mainscreen.html`):** one meaning per colour (`--info` cyan, `--run` magenta, `--heat` orange, `--danger` red, `--gain` green, `--auto` purple, `--afford` gold), listed at the top of `ui/style.css` as the rule for future UI; monospace for every number. Legend sits under DEFENSE with ICE Rating, not under RISK, because it speeds heat cooling. Panel values keep 4 significant figures (`formatSignificant`), tooltips full precision. The heat strip has one owner, `ui/view/heatStrip.ts`, shared with the coming Auto Burn panel. No re-sleeve readiness bar: there is no 0..1 progress owner. Batches B (upgrade rows by currency, Inventory stash) and C (action cards as process windows) follow, see `docs/mockups/mainscreen-plan.md`.

## Auto Burn panel

`ui/view/autoBurnView.ts` builds the owner-sourced panel data (`autoBurnViewTypes.ts`); `autoBurnStrip.ts` owns finite strip geometry (zones, the live zone, the red zone hidden until Redline Trigger). `ui/widgets/autoBurnPanel.ts` mounts persistent status, notch and protocol DOM from the parts in `autoBurnParts.ts` (LEDs, chip lists, notches, number inputs); chip lists rebuild only when target IDs change. Restart chips for an Auto-run or Overclock the sleeve does not own are `locked` (red border, no click, tooltip via `ctx.tips`). `ui/autoBurnText.ts` supplies the panel wording through `uiText.ts`, and `ui/autoBurn.css` scopes the mockup styles. `content/autoBurnSkillIcons.ts` supplies distinct protocol art, spread by `automationSkillIcons.ts`; placeholder lanes keep progress bars. `widgets/domKit.ts` exports `syncInput` so both automation widgets preserve focused input text. `autoBurnStrip.test.ts`, `autoBurnView.test.ts` and `autoBurnUi.test.ts` cover geometry, reveal/owner values and command wiring using `testing/autoBurnKit.ts` (based on `testConfig.ts`).

## Upgrades panel (B1, 2026-10-31)

One Upgrades panel replaces the two purchase widgets. Cached `sectionLayout` groups by currency (SLEEVE for credits, NETWORK for nodes), excluding action, point, corporate and re-sleeve gate purchases. `view/upgradeRows.ts` stably moves bought one-time purchases first; each partition retains base-price order. Maxed repeatables keep their place. Empty and wholly unrevealed rows show no label.

`widgets/upgradeButtons.ts` opts into tile mode through `uiText.upgradeTiles` (`parts/upgradeText.ts`, `upgradeText.ts`). Tiles retain pixel icons above a price strip, show MAX from the owner maxed flag, and show an owned badge only for repeatables with copies. Gold means affordable; teal means MAX. Existing action and skill callers retain square buttons. `sleeveWidgets.ts` compares cached row IDs element by element and appends existing buttons only when order changes; equal order allocates no order array. Tests: `upgradeRows.test.ts`, `upgradeTiles.dom.test.ts`; shared engine and mount setup: `testing/testConfig.ts`, `testing/domMountKit.ts`. No game, save, tuning or layer assumptions change.

The existing large view-model suite is split into `viewModel.test.ts` (unlock, sleeve and reveal views) and `viewModelDetails.test.ts` (general formatting, node values and critical highlights), retaining shared `testing/gameKit.ts` setup.

## Action cards as process windows (2026-10-31, presentation)

- **Title bar** (`widgets/actionCard/titleBar.ts`): icon and name, `ActionView.processId` (muted, from `view/processId.ts`: first word in full, later words cut to 3 letters, so `grow-network` is `grow_net`), the critical mark (`critText`, existing timing) and a state LED from `ActionView.state` (`processState`: `auto` = running on Auto-run, `running` = running by hand, `idle`). Wording from `uiText.action.state`.
- **Stat grid** (`stats.ts`): SPEED (`speedLine`, carries the speed tip), YIELD (`rewardLine`), RISK and COST. `ActionView.costItems` are `{ kind: 'heat' | 'cost', text }` (owner `view/actionCosts.ts`); the widget filters by kind and never reads text. A row with no lines is hidden. `infoText` and `costLine` are gone.
- **Colour:** the action colour is CSS only (`--proc`, keyed by `data-action` on the card in `styles/process.css`, `--info` fallback); it is identity, not a meaning colour. Idle cards are desaturated, running cards glow, the full fast bar streams (`.streaming`, set while `barText` is shown).
- **Controls** (`controls.ts`): each cell has an LED (`on` for a lit toggle or applied Augment), a label (`uiText.action.modes[id].label`: AUTO, OC, FOCUS, AUG), and a price strip for a `buy` cell from `SquareCellView.costText`; an `empty` cell is invisible but keeps its place. Modes and split Focus halves behave as before.
- **MODS** (`mods.ts`): the action's buyables outside the square as Upgrades-panel tiles under a vertical label, hidden until one shows.
- Presentation only: no tuning, save or mechanic change; no new assumptions about sleeves, corporations or prestige layers. Tests: `processId.test.ts`, `processCard.dom.test.ts`, `actionCosts.test.ts` (kinds).
