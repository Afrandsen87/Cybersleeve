# Context: effects

Buyable effect kinds, the effect registry, traits and the resolved effect queries.

Code: `src/core/effects/` (see `docs/review/file-map.md`). Text below is moved verbatim from the four main docs; headings name the source.

## Interface, state and config (S3)

- **Files (`src/core/effects/`):** `kinds/<family>.ts` hold the `BuyableEffect` union per family (`action`, `sleeve`, `heat`, `items`, `resleeve`, `corporation`) and `kinds/index.ts` composes it; `buyableTypes.ts` keeps `BuyableDefinition`, `BuyableId`, `Currency`, `PointCurrency` and re-exports `BuyableEffect`, so `../types` exports are unchanged. `effectTypes.ts` (traits, accumulators, hook contexts) and `effectHelpers.ts` feed `entries/*Entries.ts`, which `effectRegistry.ts` spreads into `EFFECTS` (the mapped type demands one entry per kind). `effectTraits.ts` exposes `EFFECT_TRAITS` / `traitsOf` / `assertNever`.
- **Resolvers:** `actionResolver.ts` (`resolveEffects` -> `ActionEffects`), `sleeveResolver.ts` (`resolveSleeveStats`, `earnedSpeedBeyond`; result type in `sleeveStatsTypes.ts`), `queries.ts` (`resolveLevelBonus`, `resolveNetworkGrowth`, `resolveDropChanceFactor`). `effects.ts` is a thin facade re-exporting them, so `effects/effects` imports stay valid.
- **Kind queries:** `ownedOfKind.ts` has `ownsKind` (any copy owned?), `effectsOfKind` (typed list of every buyable of a kind) and `ownedEffects` (the same with the copies owned). They replace `b.effect.kind === '...'` comparisons; `BuyableCaps` and `queries.ts` use them. Not converted (other contexts' internals, S4-S9): `actions/progression.ts` (4 XP-reduction kinds), `actions/levelRewardFactor.ts`, `automation/automation.ts`, `corporation/corporation.ts`, `items/leverageEffects.ts` and `items/drops.ts`, `resleeve/resleeveCarry.ts` and `resleeveGate.ts`, `synth/synthSleeves.ts`, `save/serialization.ts`, `config/config.ts` (validation). `resolveNetworkGrowth` stays one pass over two kinds, in configuration order, because floating-point addition depends on order.
- **State:** none; every function reads the buyables and `GameState.purchased` it is handed.
- **Config variables:** none of its own; the `buyables[]` fields below and `sleeve.*` stat bases are read through the resolvers.
- Critical chance (`criticalChance`) is NOT capped: copies add up and a total above 1 gives several critical successes per run (decided 2026-10-29). Only `criticalExtraChance` is capped at 1.

## Configuration (from docs/CONFIG.md)

### `buyables[]` – one entry per purchase
| Field | Type | Meaning |
|---|---|---|
| `id`, `name`, `description` | string | Identity and text (shown in the hover tooltip) |
| `formula?` | string | A formula that explains the effect, shown right under the description in the tooltip (e.g. `Growth factor percentage = Action level / 1000` for Self-replication). For effects that have numbers to fill in (today `networkGrowthFromActionLevel`) the tooltip also lists them under the formula. Rarity refinement has none: its tooltip is just its description |
| `actionId?` | action id | The action whose card shows this purchase; for `autoRun`/`rewardMultiplier` it is also the action the effect applies to. **Omit it for a purchase shown in the Sleeve widget.** Action effects (`autoRun`, `rewardMultiplier`, `itemDrop`, `rarityShiftFromProficiency`) require it; sleeve effects (`interfaceSpeed`, `accessLevel`) forbid it |
| `symbol?` | string | Short text on the square button (default: initials of `name`) |
| `cost` | BigNum >= 0 | Price of the first copy, in `currency` |
| `currency?` | `'credits'`, `'networkNodes'`, `'skillPoints'`, `'resleevePoints'` or `'automationPoints'` | What the price is paid in (default credits). Paying in nodes removes them from the network. `skillPoints` makes the buyable a **skill**: it is shown in the Skills tab (not on a card or in the Sleeve widgets), the points available are the points earned (0 until an action reaches level 1, then 1 + floor(log10(total of action levels))) minus the price of the skills owned, and nothing is spent from the state. Give a skill no `actionId` |
| `effect` | Action effects: `{kind:'autoRun'}`, `{kind:'rewardMultiplier', factor >= 1}` (multiplies the reward the action pays per run, nothing else: not its XP or counted runs). Sleeve effects: `{kind:'interfaceSpeed', amount >= 0}` (adds `amount` to the interface speed per copy), `{kind:'accessLevel', amount >= 1}` (adds `amount` to the access level per copy; copies stack on top of `sleeve.baseAccessLevel`). Newer: `{kind:'nodePayoutMultiplier', factor >= 1}` (what each node produces x `factor^copies`), `{kind:'iceRatingMultiplier', factor >= 1}` (ICE Rating x `factor^copies`). Auto-run buyables are toggleable in the UI. Kill servers: `{kind:'startCostReduction', perLevel in (0, 1)}` (action effect: the share of the balance the action's start cost takes is multiplied by `(1 - perLevel)^plain action level`; while owned a node cost that rounds down to 0 becomes 1 node) `{kind:'overclockChain', chain: {maxLinks >= 1 (integer), rewardPerLink > 0, nodesPerLink >= 0}}` (action effect: adds a chain to the action's Overclock; each consecutive completed run while overclocked adds a link, up to `maxLinks`; each link adds `rewardPerLink` to the reward bonus of the next run (a gain: scaled by the strength of Overclock, like `rewardBonus`) and `nodesPerLink` to the factor on the share of the balance the start cost takes, `1 + links x nodesPerLink` (a price, not scaled); a stopped action or a switched-off Overclock breaks it; the action needs a `startCost`, so its runs come one per batch, and an `overclock` rule: both checked) and `{kind:'creditSiphon', seconds > 0}` (action effect: at every start, `seconds` seconds of the current per-node income are paid for each node the start cost destroys). More: `{kind:'networkGrowth', ratePerSecond >= 0}` (nodes grow by that fraction of themselves per second; 0.000001 = 0.0001%), `{kind:'networkGrowthFromActionLevel', sourceActionId, percentPerLevel >= 0}` (nodes grow by `level * percentPerLevel` percent of themselves per second, `level` = the plain action level of `sourceActionId`, per copy; 0.001 = level / 1000 percent), `{kind:'interfaceSpeedPerLnNodes', perLn >= 0}` (base interface speed x `1 + perLn * ln(nodes)`), `{kind:'levelBonusFromSleeveLevel', sourceActionId, targetActionId}` (adds the source action's sleeve level to the target's level for speed only), `{kind:'interfaceSpeedMultiplier', factor >= 1}` (interface speed x `factor^copies`), `{kind:'heatCooldownSpeed', factor >= 1}` (heat cools `factor^copies` times as fast), `{kind:'hackingProficiencyMultiplier', factor >= 1}` (Hacking Proficiency counts `factor^copies` times as much: hacking multiplier, drop ratio shifts and the stat shown), `{kind:'runsPerSleeveXpReduction', perCopy >= 1, minRuns >= 1}` (whole numbers: every copy takes `perCopy` runs off the `progression.runsPerSleeveXp` runs one batch of sleeve XP needs, for every action, never below `minRuns`; real content: 1 and 10, so 90 copies reach the floor), `{kind:'iceRatingFromActionLevel', sourceActionId, perLevel > 0}` (adds `perLevel x plain action level of the source x copies` to the base ICE Rating, before the `iceRatingMultiplier` buyables multiply it; real content: Hardened payload on Push malware, price 10,000, `perLevel: 10`), `{kind:'actionXpReduction', amount in (0,1)}` (every ACTION level needs `amount x copies` less XP, capped by `progression.maxSleeveXpReduction`; sleeve levels are unaffected), `{kind:'itemDropChanceMultiplier', itemId, factor >= 1}` (the chance of a drop at all of every drop rule of that item x `factor^copies`, at most 1), `{kind:'nodePayoutFromItems', itemId, rarityId, perItem >= 0}` (node payout x `(1 + perItem x the number of that item and rarity held)`), `{kind:'backChannel', itemId, rarityId, molesPerItem > 0, cooldownBoost >= 0}` (lets the player give up that item and rarity for `molesPerItem` Moles each; while Moles remain heat cools `cooldownBoost` faster, one Mole per point of heat), `{kind:'sleeveXpReduction', sourceActionId, perLevel > 0}` (the XP every sleeve level of every action except the source needs is DIVIDED by `1 + perLevel * source sleeve level * copies`; no ceiling, kept finite at 1e300; not part of the `maxSleeveXpReduction` clamp). Action effect `{kind:'itemDrop', drop:{itemId, chance in [0,1], rarityWeights}}` (each completed run of the buyable's action has `chance` to drop one `itemId`; the rarity is drawn by `rarityWeights` (required for an item with rarities, forbidden for one without), a relative weight per rarity id, >= 0, at least one > 0, normalised, a missing rarity weighs 0; applies once whatever the number of copies). Action effect `{kind:'criticalBoost', factor >= 1}` (multiplies the `xpMultiplier` and `rewardMultiplier` of the action's critical successes by `factor`; once, whatever the copies; real content: Persistence, 500,000, 3). Action effect `{kind:'criticalLink', targetActionId}` (every critical run of the action banks one guaranteed critical success for the target action, spent by that action's next completed runs; once; real content: Ransomware, Push malware to Grow network). Sleeve effect `{kind:'overclockHeatFactor', targetActionId, factor >= 1}` (lowers the target action's Overclock `heatPerRunFactor` to `factor` when the rule's own factor is higher; the lowest owned wins; real content: the skill Obfuscation, Push malware, 2). Action effect `{kind:'rarityWeightBonus', itemId, amount > 0, rarityId?}` (sleeve effect: adds `amount` per copy to the drop weight of that rarity of the item, or of every rarity without `rarityId`; real content: Deep Files rare, Sealed Archives legendary, Black Ledger crisis, 0.1 each), `{kind:'rarityShiftFromProficiency', fractionPerOrder in (0,1]}` (for every whole order of magnitude of Hacking Proficiency, `fractionPerOrder` of each rarity's weight moves to the next rarity, all amounts worked out up front and moved at once; shifts the drop ratios of the buyable's action; real content: 0.01)  Re-sleeve tree: `{kind:'actionXpReductionFromSleeveLevel', remainingPerOrder in (0,1), maxReduction in [0,1)}` (sleeve effect: every ACTION level of an action needs `1 - remainingPerOrder^log10(sleeve level of that action)` less XP, at most `maxReduction`; multiplies with `actionXpReduction` and is outside its cap; real content: Sleeve Euphoria, 0.5 and 0.999, so 50% at level 10 and 75% at 100), `{kind:'synthSleeves'}` (gives one synthetic sleeve when bought, copied from the last finished run, and one more with every later re-sleeve) and `{kind:'placeholder'}` (does nothing; no real skill uses it now). A buyable paid in `resleevePoints` is a **re-sleeve skill**: it is kept through re-sleeving, listed in the tree on the Skills tab, and its `requires` draw the tree | What each owned copy does. Output multipliers compound: `factor^copies` |
| `requires?` | id[] | Buyables that must be owned first; until then the buyable is hidden. For a skill this is the **reveal gate**: the purchase that makes it useful (until it is owned the skill's text reads `???`) |
| `revealAfterResleeves?` | integer >= 0 | Finished sleeve-runs (`GameState.runs.length`) needed before the buyable is available; 1 = from the second sleeve run on (real content: Faster conditioning, Skill transfer). Validated in `core/config/config.ts`, checked in `Shop.isAvailable` |
| `parents?` | id[] | Skill-tree edges, skills only (paid in points): the skills that must be owned before this one can be bought. A skill reads only when its `requires` are owned **and** every parent reads, so the masking runs down the tree. Every parent is in the **same `branch`** as the skill, so each parent has a line drawn to it (validated); parents form no cycle (validated together with `requires`) |
| `branch?` | string | The skill-tree branch (lane) the skill is drawn in; ids are in `content/ids.ts` (`BRANCH_*`), titles in `uiText.skills.branches`, colours in `ui/style.css` (`--branch-<id>` and a `.skill-lane[data-branch="<id>"]` rule). Skills without one share a general lane |
| `maxPurchases?` | integer >= 1 or `Infinity` | Copies allowed (default 1) |
| `costGrowth?` | number >= 1 | Price multiplier per copy owned: price = `cost * costGrowth^owned` (default 1) |

## Decisions (from docs/DECISIONS.md)


*Group: Decided 2026-10-25 (by the user, after the second review)*
- **No global reward multiplier.** A lever applies to one named kind of reward and nothing else. Today the only one is `global.creditMultiplier` (credits earned: run rewards paid in credits and passive network income). It never touches nodes, ICE Rating, Legend, or the interface-speed and node-payout bonuses. A lever for another kind is its own named setting, and which kinds a lever scales is stated in `REWARDS` (`core/actions/rewards.ts`).

*Group: Decided 2026-10-25 (by the user, after the second review)*
- Every reward kind and every buyable effect kind is described once as data (`REWARDS`, `EFFECT_TRAITS`); code asks the descriptor instead of comparing kind names. Resolver `switch`es over effect kinds end in `assertNever` so a new kind cannot be forgotten.

*Group: Decided 2026-10-25 (by the user, after testing)*
- **No general output multiplier.** The old `outputMultiplier` also scaled XP and counted runs, and made Practice Hacking's speed grow exponentially; it was removed. A `rewardMultiplier` buyable scales **only the reward its own action pays per run** (e.g. the nodes Grow Network pays). Every future multiplier states exactly what it multiplies; code never applies one multiplier to everything an action does.

*Group: Decided 2026-10-26 (by the user, after the full review)*
- **Buyable effects live in one registry** (`core/effects/effectRegistry.ts`): a new effect kind is a union member plus ONE registry entry (traits, validator, action and sleeve hooks). `effects.ts` has no `switch` over kinds. A kind read only by a dedicated query leaves the hooks out.

*Group: Decided 2026-10-27 (by the user, new Anonymity skills)*
- New effect kinds (registry entries in `core/heat/heatEffects.ts`): `burnLeadFlatHeat`, `idleHeatCooldown`, `idleHeatCooldownAction`, `moleAggregation`, `heatTaxCap`. The six new skills use placeholder icons borrowed from related skills until they get their own art.

*Group: Decided 2026-10-27 (by the user, more re-sleeve skills)*
- New effect kinds (entries in `core/resleeve/resleeveEffects.ts`): `buyableCapBonus`, `focusStacking`, `synthsPerResleeve`, `interfaceSpeedPerLnSynths`, `synthXpBoost`, `perfectCopies`, `corporationSpeedPerLnSynths`, `unlocksSynthPurchase`, `autoRepurchase`, `keepsAutomation`, `carriesProficiency`, `carriesIceRating`. The new skills use placeholder icons borrowed from related ones. No save version bump: every new saved field is optional on read.
